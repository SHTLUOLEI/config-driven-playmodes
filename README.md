# config-driven-playmodes

> 当项目里有 N 个小玩法，如何只写一次「加载→演出→游玩→结算→释放」，让玩法作者只实现 4 个方法。

## 问题

小玩法合集类游戏（本 demo 提炼自一个 8 个小游戏模块的合集项目——TapTap 聚光灯 GameJam 参赛作品《打卡喵》——的重构推演）最容易腐烂的地方不是玩法本身，而是**玩法之间的胶水层**：每个玩法各写一套加载状态机，暂停/重试/断点恢复的行为逐渐发散，改一个公共需求要动 N 处。

## 思路

把「玩法差异」全部推到配置表，运行层只保留一份协议：

```
┌────────────┐   配置表(id/演出beats/私有参数)   ┌──────────────┐
│  配置表     │ ───────────────────────────────→ │  运行层       │
└────────────┘                                   │ PlayModeRuntime
┌────────────┐   契约 4 方法                      │  · Begin: 备帧→演出→放行
│  玩法实现   │ ←──────────────────────────────── │  · End:   停止→收尾→释放
│ IPlayMode  │   结果回传(不直接碰存档)           └──────────────┘
└────────────┘
```

关键约束：

1. **玩法不碰存档**——结算通过 `PlayContext.Report` 回传，持久化由运行层的事务入口统一执行，避免各玩法写出不一致的进度；
2. **演出与玩法分离**——Intro/Outro 是配置数据，由运行层统一按节奏推进，玩法作者不用关心；
3. **新增玩法 = 注册一行 + 配置一行**——不需要触碰运行层代码。

## 运行

```bash
dotnet run
```

`Demo.cs` 演示一个「点击反应」玩法从配置驱动到结算上报的完整链路。

## 为什么不用 ScriptableObject / 行为树

ScriptableObject 把配置绑死在编辑器资产里，热更新和运营改配置都要出包；行为树对「线性演出 + 单状态机」的小玩法属于过度设计。JSON/Luban 类表格配置对迭代与热更更友好，这也是该项目里的实际选择。
